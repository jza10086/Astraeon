# 方块数据存储初筛：2026-09-16

> 历史测量记录：旧 GDScript 实现与专属运行器已于 2026-09-18 删除，下文路径和命令描述当时状态，不是当前可运行入口。

## 结论

当前活跃区块段推荐 **DIRECT16**。保留 DIRECT32 作为直接数组速度对照，保留 PALETTE 作为实验性压缩方案。未接入真实地形渲染，不据此承诺游戏 FPS。

推荐结构：每种方块共享 Resource 定义 → 注册表复制为运行时 ID/属性表 → 每个 16³ 段使用 DIRECT16，格子仅保存 0..65535 状态 ID。没有给每格创建 Resource 或节点。特殊方块实例仍待实际功能实现。

Factory 提供显式推荐常量 RECOMMENDED_ACTIVE_BACKEND，创建和转换仍可以选择三种后端，没有自动切换。

理由：
- 三类数据中，DIRECT16 顺序读取比 DIRECT32 慢约 2.1%～3.1%，六邻居读取慢约 2.9%～6.3%；数组载荷从每段 16 KiB 减为 8 KiB。
- 普通修改批次接近，不能根据少量尾部波动宣称某后端永远更快。
- 地形/建筑中 PALETTE 顺序读取比 DIRECT16 慢约 34%～36%，新增状态扩容中位数约 1.47 ms，批量初始化也更慢。
- PALETTE 对纯色和低多样性数据很省内存，但 64 状态建筑的私有内存增量中位数高于 DIRECT16；字典、对象及分配器成本不能用紧凑数组大小代替。三次进程内存样本有波动，该结果不等于精确的单对象堆大小。

现阶段采用一种直接数组后端更容易维护。冷段调色板、纯色段专用表示可在真实驻留规模出现内存压力后单独评估；本轮没有实现或验证这些混合策略。

## 正确性与选型边界

- 现有回归 PASS：52511 次检查，覆盖三种后端。
- 每个进程校验初始数据、编辑重放和新状态写入后的邻格；27 个进程 valid=true。
- 每个数据集/种子组合三种后端的读取校验和一致。
- 当前字段容量统一限制 65536 种状态；DIRECT32 的更大潜在整数容量未在契约中开放。
- Resource 配置加载格式未比较；本次比较的是区块实例数据存储。
- 没有发布构建、真实网格、碰撞、光照、渲染帧时间或 VoxelBuffer 原生后端对照。推荐适用于当前 GDScript 数据层基线，后续集成后仍应验证端到端延迟。

## 复现

先通过项目技能解析引擎，然后执行：

~~~powershell
$blockEngine = ./.agents/skills/godot-project-tooling/scripts/resolve_godot.ps1 -ProjectPath . | ConvertFrom-Json
python tools/run_block_storage_suite.py --run --engine $blockEngine.path --repeats 3 --budget-seconds 300
~~~

驱动支持 --deadline-utc 为整个任务设置绝对截止时间；每个子进程另有最多 90 秒上限。超过预算保留已完成样本并标记未完成，不能据部分结果冒充完整矩阵。较慢机器可以显式增加预算。
